# Vault schema

The project's notes live in the `vault_dir` printed by `vault resolve`, scratch files in the `work_dir`. Always
write through the real paths `vault resolve` prints, never through a symlink to them.

## Layout

`vault resolve` also prints `layout` and `link_prefix` (`<L>` below):
- **shared** (`<L>` = `<slug>/`): `vault_root` holds every project; `vault_dir` = `<vault_root>/<slug>`, and the
  root has a generated `index.md` (L0: projects list) and a `.work/` scratch dir.
- **repo** (`<L>` is empty): `vault_dir` is the vault itself (often `<repo>/vault`); there is no L0, and `work_dir`
  lives outside it.

```
<vault_dir>/
  _meta.json                managed by the CLI: never edit by hand
  index.md                  L1: the project overview (hand-written, ≤ 1.2k tokens)
  glossary.md               domain terms
  log.md                    append-only history (the CLI appends; you never edit)
  features/<name>.md        L2: product features (what the user gets, how it works, which modules)
  guides/<name>.md          L2: how-tos ("how to add a scan step", "how config overrides resolve")
  problems/<name>.md        L2: bugs, gotchas, tech debt, limitations
  decisions/dec-NNNN-<name>.md  L2: non-architectural decisions (process, tooling, local implementation; MADR-lite)
  conventions/<name>.md     one rule each, level must|should (guardrails)
  architecture/<section>.md  SAD after arc42, one note per section (guardrails read C-n / P-n items)
  architecture/adr/adr-NNNN-<name>.md  architectural decisions (ADR, MADR-lite; arc42 §9)
  proposals/<name>.md       change proposals for a convention or a SAD section (await the user)
  modules/<name>.md         L3: code-level notes, one per package/lib/area
  lessons/<kebab-name>.md   lessons learned in retros (one rule each, counted across retros)
  retros/<YYYY-MM-DD>-<kebab-topic>.md  one retrospective per verified task (search skips them unless --type retro)
  features/<feature>--<aspect>.md  L3 sub-note when a feature's "How it works" outgrows its budget
  modules/<module>--<area>.md      L3 sub-note for a large module
  */_index.md               hubs, generated by `vault commit`: never edit (lint accepts links to the hub of any
                            existing folder before the first commit writes it)
<work_dir>/                   scratch (plans, reports, worktree), not in git, not docs
```

File names are kebab-case. ADRs and decisions share one number sequence: `vault next-id adr|decision --name <x>`
prints the next free path (`architecture/adr/adr-NNNN-x.md`, `decisions/dec-NNNN-x.md`). Older decisions keep their
`adr-NNNN` names. The type follows the deepest folder (`architecture/adr/` → `adr`, `architecture/` →
`architecture`). Move a note only with `vault mv <old> <new>`: it rewrites every wikilink to it, adds the old path to
`aliases` and fixes `type`; then `vault commit`.

### Schema version

`_meta.json` has `schema` (a missing field means 1); the current schema is 2 (`vault version --json` prints it). A
schema-1 vault lacks the conventions / architecture split: `vault lint` reports an error, `vault status` and the
session context say `vault needs migration: /vault migrate`. Never edit `schema` by hand; the migration sets it.

Migrations (`ops/migrate.md`, only on the user's `/vault migrate`) are ordered step lists per source schema
(`MIGRATIONS` in `lib/vaultlib/migrate.py`; a future schema appends its own list):
- `vault migrate --plan [--dry-run] [--format text|json]`: refuses when the vault has uncommitted changes, records
  the vault's HEAD as the `checkpoint`, creates the new folders and hubs, writes `<work_dir>/migrate-plan.json` and
  prints `{status, slug, from, to, checkpoint, rollback, steps[{name, from, phase, description, done}], changes,
  decisions[{path, link, title, summary, status, kind, tags, code_refs}], plan_file}`. `status`: `planned`,
  `resuming` (a migration is in progress), `dry-run` or `up-to-date` (nothing to do).
- `vault migrate --apply <decisions.json> [--dry-run] [--format text|json]`: moves every existing decision with
  `verdict: accepted, class: adr` to `architecture/adr/adr-NNNN-<name>.md` (number kept; an unnumbered note gets
  the next free one; links rewritten; old path in `aliases`), sets `kind` on those accepted as `class: decision`,
  regenerates hubs and lints. Lint errors → exit 1, `status: lint-failed`, schema unchanged: fix and re-run.
  Clean → `schema: 2`, a `migrations` history entry in `_meta.json`, commit `migrate schema 1→2`
  (`status: migrated`).
- Progress lives in `_meta.json` `migration` (`from`, `to`, `checkpoint`, `done` steps, `moves`), so a re-run after
  a failure resumes; every step is idempotent. A vault already at schema 2 is a no-op.
- Rollback: the `rollback` command restores the project dir to the checkpoint (`git restore --source=<sha>` +
  `git clean`); after the migration commit, `git revert` it instead.

`<work_dir>/candidates.json` (written by `init-candidates`) and `<work_dir>/decisions.json` (the user's answers,
written by the main session in `init-confirm`) carry guardrail candidates through `init` and `migrate`; their
formats are in `ops/init-candidates.md` and `ops/init-confirm.md`.

### Harness pseudo-project `_harness`

Cross-project lessons (`scope: harness`: how the coding agents work for this user, not about one repo) and retros of non-repo
sessions live in the project `_harness`. Shared layout: `<vault_root>/_harness`. Per-repo layout:
`$AGENT_VAULT_HARNESS_DIR` (the `_harness` dir itself, or a root holding it; legacy `$CLAUDE_VAULT_HARNESS_DIR`),
else an existing `~/claude-vault/_harness`, else `${XDG_DATA_HOME:-~/.local/share}/agent-vault/_harness`.
Create it with `vault resolve --project _harness --create` (works outside any repo); its links are
`[[_harness/lessons/x]]`. Projects whose slug starts with `_` never get `paths`/`remotes`, so no directory resolves
to them: always address them with `--project _harness`.

## Frontmatter

Every note except hubs and log starts with this block. Values are JSON-compatible: quote strings that contain `:`, `#`
or quotes, and write lists as JSON arrays.

```yaml
---
title: "Scan flow"
type: feature
status: active
summary: "Guided multi-step vehicle photo capture with on-device damage detection."
aliases: ["scanning", "vehicle scan", "capture flow"]
code_refs: ["libs/scan/src/lib/scan.facade.ts", "libs/camera/src/lib/camera.service.ts"]
verified: 57bc3ef59a1d
---
```

| Field | Rule |
|---|---|
| `title` | Human title. |
| `type` | `project` (index.md), `feature`, `guide`, `problem`, `decision`, `adr`, `convention`, `architecture`, `proposal`, `module`, `lesson`, `retro`, `glossary`. Must match the folder. |
| `status` | feature/guide/module: `active`, `draft`, `deprecated` · problem: `open`, `resolved`, `wontfix` · decision and adr: `accepted`, `superseded`, `inferred`, `proposed` · convention: `active`, `proposed`, `inferred`, `retired` · architecture: `active`, `proposed`, `inferred` · proposal: `open`, `applied`, `rejected` · lesson: `active`, `promoted` (rule moved into the harness), `retired` · retro: `recorded` · project/glossary: `active`. |
| `summary` | ONE sentence. Search results and hubs show it, so make it specific: what, not "This note describes…". |
| `aliases` | Synonyms people would search for (user words, old names, abbreviations). This is what makes search find the note. |
| `code_refs` | Repo-relative paths of the specific files the note's claims depend on (≤ ~12). A module root may be `libs/x/` with a trailing slash. Avoid `**` globs: they mark the note stale on every change. Staleness is computed from these. Lint resolves them at the target ref; a ref that exists only in the repo working tree (a change not committed yet, e.g. during a post-pass `sync`) is a warning, not an error. |
| `verified` | Commit (12 chars) of the target branch at which the note was checked against code. Set by `vault commit --stamp`; leave it empty in new notes (`verified: ""`) unless told otherwise. |

Lesson and retro notes add flat fields (scalars and lists only):

| Field | Rule |
|---|---|
| `scope` (lesson) | `project` (this repo) or `harness` (lives in `_harness`). |
| `audience` (lesson) | Who must follow it: any of `implementer`, `orchestrator`, `triage`, `reviewer`, `qa`, `retro`. Session context shows lessons for `implementer`/`orchestrator`; `vault lessons --audience <a>` feeds agent task files. |
| `category` (lesson) | `efficiency`, `correctness`, `process`, `tooling`, `environment` or `communication`. |
| `occurrences` (lesson) | Integer ≥ 1 (lint error otherwise): the number of retros in which this failure pattern happened. |
| `first_seen`, `last_seen` (lesson) | `YYYY-MM-DD`. An `active` lesson not seen for 90 days → lint warns `stale lesson`. |
| `evidence` (lesson) | Links to the retros that saw it. |
| `proposal_status` (lesson) | `none`, `open` (awaits the user: `vault lessons --proposals`), `applied`, `rejected`. Set by `vault proposal accept\|reject`, never by hand once open. |
| `proposal_kind` (lesson) | `none`, `rule-promotion` (move the rule into CLAUDE.md / AGENTS.md / a skill / an agent), `harness-change`, `repo-change`. |
| `proposal_target`, `promoted_to` (lesson) | Target file (and section) of the proposal; `promoted_to` is set on accepting a rule promotion. |
| `session`, `run`, `date`, `branch` (retro) | agent session id, verify-loop run id, `YYYY-MM-DD`, git branch. |
| `change_size`, `qa_scope`, `review_tier`, `attempts` (retro) | From the run's triage/plan: `small\|medium\|large`, `none\|checks\|run\|browser`, `standard\|deep`, integer. |
| `outcome` (retro) | `passed`, `accepted`, `abandoned` or `skipped` (lint warns otherwise). |
| `tokens_total`, `tokens_main`, `tokens_verify`, `cost_usd`, `duration_min` (retro) | Numbers from `metrics.json`. |
| `lessons` (retro) | Links to the lessons it created or updated. |

Retros, proposal notes and notes with an open proposal are exempt from the orphan warning; lessons are not (link them from their retros).

Convention, architecture, ADR and proposal notes add:

| Field | Rule |
|---|---|
| `level` (convention) | `must` (a violation blocks review) or `should` (a suggestion). Required (lint error). `must` only when the user said so ("must", "always", "never"); never set it on your own. |
| `rule` (convention) | One imperative sentence. Required (lint error). Guardrails print it. |
| `scope` (convention, optional on adr) | JSON list of repo globs the rule covers (`["src/api/**"]`); `[]` = the whole repo. Lint warns on a glob that matches no file. |
| `source` (convention) | `user`, `inferred` (deduced from code), `retro`, `init-confirmed`. |
| `adr` (convention) | Optional link to the ADR the rule comes from. |
| `section` (architecture) | One of `goals`, `constraints`, `context`, `building-blocks`, `runtime`, `deployment`, `crosscutting`, `quality`, `risks`; one note per section (lint error otherwise). |
| `supersedes`, `superseded_by` (adr) | Links between ADRs; a `superseded` ADR needs `superseded_by`. |
| `kind` (decision) | `process`, `tooling` or `implementation`. A decision tagged `architecture`/`adr` or with `kind: architecture` makes lint warn: move it to `architecture/adr/`. |
| `proposal_status`, `proposal_kind`, `proposal_target` (any note) | As for lessons; kinds add `adr-new`, `convention-new`, `convention-change`, `sad-change`. |
| `base_hash` (proposal) | `vault hash <target>` of the target version the proposal was written against. |

## Conventions, architecture, ADRs and decisions

- **Convention**: one durable rule about how code in this repo is written (layering, naming, error handling, an API
  pattern). One note per rule.
- **ADR** (`architecture/adr/`): a choice that shapes the system's structure, boundaries, dependencies, integrations
  or quality attributes (arc42 §9): "all DB access goes through repositories", "events over direct calls between
  services", "Postgres, not Mongo".
- **Decision** (`decisions/`): everything else: process, tooling, a local implementation choice ("jest over
  vitest", "release from master", "retry 3 times in the uploader").
- When unsure between ADR and decision, ask: would breaking it change a box or an arrow in the C4 diagrams? Yes →
  ADR.

### Guardrails

`vault guardrails [--paths <path> <path>…] [--format bullets|json] [--budget N]` (default 1800 chars) returns what a
change must respect (integration contract 2). `--paths` takes space- or comma-separated repo paths and can repeat
(`--paths a.ts b.ts`, `--paths a.ts,b.ts` and `--paths a.ts --paths b.ts` are the same):
- conventions with status `active` or `inferred` whose `scope` matches any path (all of them without `--paths`),
  `must` first;
- the `C-n:` items of `architecture/constraints.md` and the `P-n:` items of `architecture/crosscutting.md` (status
  `active`/`inferred`), always as `must`;
- `accepted` ADRs of `architecture/adr/` (global unless they declare `scope`), newest first.

Plain `decisions/`, `proposed` and `retired` notes never count. Over the budget, `should` conventions go first, then
the oldest ADRs; `must` items always stay. Bullets: `- MUST [[<link>]] — <rule> (scope: src/api/**)`, `- SHOULD …`,
`- ADR [[<link>]] — <first line of ## Decision>`, with ` (inferred)` for inferred notes. JSON:
`{"contract":2,"schema":N,"conventions":[…],"architecture":[…],"adrs":[…]}`, each item
`{link,title,kind,level,rule,scope_match,status}` (`kind`: `convention`, `constraint`, `principle`, `adr`;
`scope_match`: the globs that matched, `[]` = global). An uninitialized project prints nothing. The session context
adds a digest (≤ ~900 chars: must-conventions, C-/P- items, the 5 newest ADRs) whose last line is never trimmed:
`Guardrails CLI: <absolute path>/skills/vault/bin/vault guardrails --cwd <resolved repo root> --paths <file> <file>... --format bullets`
(the CLI path has symlinks resolved; paths are quoted when they have spaces; when a very long repo root would not fit,
`--cwd` is dropped; items are trimmed before this line), so agents can call the CLI even when `vault` is not on PATH.
The digest comes after the lessons block, so it ends the session context.

### Proposals

The keeper never sets `level: must`, `status: active` (convention) or `status: accepted` (ADR) itself, and changes
existing conventions, SAD sections and ADRs only through proposals the user accepts:
- `adr-new` / `convention-new`: the proposal is the new note itself in its folder, `status: proposed`,
  `proposal_status: open`, `proposal_kind: adr-new|convention-new`. A new convention from sync is `level: should`.
  Accepting makes it `accepted` / `active`.
- `convention-change` / `sad-change`: a `proposals/<name>.md` note (`type: proposal`, `status: open`) with
  `proposal_target: "[[<L>conventions/x]]"` (or a SAD section), `base_hash: <vault hash of the target>` and the full
  new target text in a 4-backtick fence under `## Proposed note` (4 backticks so Mermaid fences inside survive), plus
  `## Why`.
- `vault proposal accept <note>` on a change proposal first compares `base_hash` with the target. Equal → the target
  is replaced, the proposal becomes `applied`, the vault is committed. Different → nothing is written, the CLI prints
  `needs-rebase: …` and exits with code **3**; the dispatcher then runs `ops/proposal-rebase.md`, shows the user the
  diff and only then accepts again.
- `vault lessons --proposals` lists every open proposal (lessons and other notes).

### C4 diagrams (Mermaid)

`context` → `C4Context`, `building-blocks` → `C4Container` (and `C4Component` for one container), `runtime` →
`sequenceDiagram`, `deployment` → `C4Deployment`, each in a ```` ```mermaid ```` block. Keep each diagram to ~15
elements, use no style macros (`UpdateElementStyle`, …), and give elements the aliases of the module notes they stand
for (`Container(auth, "auth", …)` ↔ `modules/auth`). Lint only checks that the block exists.

## Body rules

- **Start with `## Summary`** (2–3 sentences) so a reader can stop early.
- **Budgets** (≈ chars/4): index ≤ 1200 tokens, L2 notes ≤ 1000, modules and sub-notes ≤ 2500, glossary ≤ 2500, lessons ≤ 500, retros ≤ 800, conventions ≤ 500, architecture sections ≤ 1500, ADRs ≤ 1000, proposals ≤ 2500. Over budget → split into a sub-note and link it.
- **English, dense, factual, present tense.** No filler, no marketing, no restating the obvious.
- **Cite code as `path` + `Symbol`**, e.g. ``libs/auth/src/lib/auth.service.ts`` → `AuthService.refreshToken()`. Never line numbers. Every non-trivial claim about behavior must be traceable to a cited file or symbol. If something is a guess, write `Unverified:` before it.
- **Be exact about conditions.** For a magic number, ID, threshold or flag, state the exact condition that uses it ("fetch runs only when PMI 572 is missing; 573 alone doesn't skip it"), not a vague "reads 572/573".
- **Links are vault-absolute wikilinks**: `[[<L>modules/auth]]`, optionally `[[<L>modules/auth|auth module]]` or `[[<L>features/scan#How it works]]`, where `<L>` is the `link_prefix` from `vault resolve` (`<slug>/` in a shared vault, empty in a per-repo vault). Never bare `[[auth]]`.
- **Link both ways where it matters**: feature → its modules, module → features that use it ("Used by"), problem/decision → affected modules or features, index → features, guides, key modules. Every content note needs at least one inbound link from another content note (hubs don't count), otherwise lint reports an orphan.
- **Don't duplicate**: the repo's `CLAUDE.md` / `AGENTS.md` / README cover commands and setup, so link them (in backticks) instead of copying them. One fact lives in one note; others link to it.
- **No secrets**: no tokens, keys, passwords or customer data.

### decision (decisions/dec-NNNN-name.md) and adr (architecture/adr/adr-NNNN-name.md)
```markdown
## Summary
**Date:** YYYY-MM-DD · **Source:** session | repo docs | inferred from code
## Context
## Decision
## Options considered
- A: pros / cons
## Consequences
## Related
```
An `inferred` decision was reconstructed from code. Replace `**Source:**` with
`**Evidence:** <paths/symbols/commits> · **Confidence:** high | medium | low`. Leave out "Context" or "Options
considered" when the code doesn't tell you; never write "Not recorded". A short inferred ADR is fine. An ADR's first
line under `## Decision` is what guardrails print: make it one self-contained sentence. A superseding ADR sets
`supersedes`, and the old one gets `status: superseded` and `superseded_by` (through a proposal).

## CLI for lessons and coverage

- `vault lessons --format json` objects: `{link, path, title, rule, occurrences, last_seen, scope, audience, category,
  proposal_status, proposal_kind, proposal_target}`; `vault covering --format json`: `{link, title, summary, type, stale}`.
- `vault lessons [--audience A] [--limit N] [--format bullets|json] [--proposals] [--no-harness]`: active lessons
  of the project (default N 5), then `_harness` lessons up to ceil(N/2). `--proposals` lists lessons with
  `proposal_status: open` (project + harness) as `- [[<link>]] — <kind> → <target>: <summary>`. Outside an
  initialized project: harness only. Nothing → empty output.
- `vault version [--json]`: `agent-vault <version> (contract 2)`, or JSON `{name, version, contract, contracts,
  schema, skill_dir, cli}` (`contracts`: every contract this CLI serves, `[1, 2]`; `schema`: the vault schema).
  `vault resolve` also prints `vloop` (`{cli, version, contract}` of the optional agent-verify-loop CLI, else null).
- `vault covering <path>… [--format bullets|json] [--limit N]`: notes whose `code_refs` match any path,
  `- [[<link>]] — <title>: <summary>[ (stale)]`.
- `vault proposal accept|reject <note>`: accept → `proposal_status: applied` (a `rule-promotion` also becomes
  `status: promoted`, `promoted_to: <proposal_target>`; `adr-new` → `accepted`, `convention-new` → `active`; a
  change proposal replaces its target, or exits 3 with `needs-rebase` when the target changed); reject →
  `proposal_status: rejected`; then commits. Only after the user approved it.
- `vault hash <note>`: the `base_hash` of a note. `vault mv <old> <new> [--dry-run] [--json]`: move a note and
  rewrite links. `vault next-id adr|decision [--name x]`: next numbered path.
- Session context (`vault context --hook`) appends a lessons block (before the guardrails digest): up to 5 project and 3 harness lessons for the
  `implementer`/`orchestrator` audience (`promoted`/`retired` never shown) plus the count of open proposals. Agents
  named `vault-*` and `verify-*` (with or without a plugin namespace such as `agent-vault:` or
  `agent-verify-loop:`) get no session context.
